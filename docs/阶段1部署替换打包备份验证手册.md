# 全栈打包操作指南（Aurora + Luoyun 阶段 1）

> 适用项目：Luoyun Provider + Aurora Spring Boot + Aurora Admin  
> 生产目录：`/home/blog/aurora`  
> 部署方式：Docker Compose  
> SSH 入口：本地别名 `blog`，仅允许公钥登录  
> 整理日期：2026-08-29

## 1. 文档目标

本文基于阶段 1 已经实际走通的项目结构和命令，完整说明从开发机打包到生产回滚的全栈发布流程，重点回答以下问题：

1. 开发机上需要构建和打包哪些文件；
2. 上传生产服务器后怎样验证发布包没有损坏；
3. 替换 JAR、管理端和 Compose 配置前怎样做可恢复备份；
4. 怎样构建并试运行 Luoyun Provider；
5. 怎样让 Spring Boot 通过 `127.0.0.1:5680` 调用 Provider；
6. 怎样应用后台接口权限 SQL；
7. 怎样逐层验证容器、接口、管理页面、内存和凭证安全；
8. 发生故障时怎样回滚。

本文不包含阶段 2 的歌曲入库、歌词队列和数据库结构迁移。

### 1.1 实际项目与产物对应关系

| 层次 | 实际目录 | 构建命令 | 构建或发布产物 |
|---|---|---|---|
| Vue 管理端 | `aurora-vue/aurora-admin` | `npm ci`、`npm run build` | `dist/`，发布时压缩为 `aurora-admin-dist.tgz` |

阶段 1 只修改 Aurora Admin，因此本指南不额外打包 `aurora-blog`。这不是遗漏，而是保持现有部署边界，不擅自扩大前端发布范围。

### 1.2 最长链路与停止原则

```text
本地工具检查
  → Vue 构建
  → Spring Boot 打包
  → Provider 校验与归档
  → 组装发布包并生成 SHA-256
  → scp 上传
  → 服务器资源与容器预检
  → 校验、备份、保留旧镜像
  → 解压或复制发布物
  → Docker 构建与 Compose 启动
  → 按需重载 Nginx
  → 分层验证
  → 完成记录或回滚
```

任何一步出现未解释的失败都先停止，不要带着损坏产物、失败备份或不健康容器继续执行后续替换。

## 2. 阶段 1 的功能边界

阶段 1 只建立只读接入链路：

```text
Aurora Admin
    │
    │ /api/admin/music/netease/*
    ▼
Aurora Spring Boot
    │
    │ Bearer Token + http://127.0.0.1:5680/v1/*
    ▼
Luoyun Provider
    │
    ▼
网易云音乐
```

阶段 1 已实现：

- 在管理后台输入 `MUSIC_U` 登录；
- 查询登录状态和退出登录；
- 读取当前账号的歌单；
- 读取歌单详情和歌曲列表；
- 在管理后台选择整张歌单或部分歌曲；
- Provider 只监听容器共享网络命名空间内的 `127.0.0.1:5680`；
- Spring Boot 与 Provider 使用至少 32 字符的服务令牌通信；
- `MUSIC_U` 只保存在 Provider 的受限持久化目录，不返回页面、不写日志。

阶段 1 明确不做：

- 不写入 Aurora 音乐表；
- 不创建本地歌单；
- 不下载音频；
- 不上传封面或歌词；
- 不公开 Provider 端口；
- 不把网易云作为博客前台播放时的实时依赖。

## 5. 开发机：构建前验证

先确认工具版本：

```bash
node --version
npm --version
mvn --version
java -version
```

命令说明：

- `node --version`：显示 Node.js 版本。Luoyun 当前 `package.json` 要求 Node.js 24 或更高版本。
- `npm --version`：显示 npm 版本，用于判断当前环境能否正确读取锁文件。
- `mvn --version`：显示 Maven 版本、它实际使用的 Java 版本和平台信息。
- `java -version`：单独确认 Java 运行时。Aurora 后端现有生产 Dockerfile 使用 Java 8，不要在没有兼容性验证时生成更高版本字节码。

### 5.1 Luoyun

在 Luoyun 项目根目录执行：

```bash
npm ci
npm run typecheck
npm test
```

命令说明：

- `npm ci`：严格按照 `package-lock.json` 安装依赖，并清理已有 `node_modules`；适合可复现构建。若 `package.json` 与锁文件不一致，它会失败而不是自动改写锁文件。
- `npm run typecheck`：执行项目定义的前端与服务端 TypeScript 类型检查，不生成运行产物。
- `npm test`：运行当前 `node:test` 单元测试，包括 Provider 鉴权相关检查。

阶段 1 最终验证要求：

- TypeScript 类型检查通过；
- Provider 鉴权测试通过；
- 不需要真实 `MUSIC_U` 就能完成的单元测试全部通过；
- 不在构建日志中打印凭证。

### 5.2 Aurora 后端

在 `aurora-springboot` 目录执行：

```bash
mvn -B -DskipTests package
```

命令说明：

- `mvn`：运行 Maven。
- `-B`：使用批处理模式，关闭交互式进度显示，便于阅读和保存构建日志。
- `-DskipTests`：沿用阶段 1 原命令，跳过测试执行；通常仍会编译测试代码。高风险改动应先单独执行测试，不要把跳过测试理解为测试通过。
- `package`：执行 Maven 生命周期的打包阶段，编译项目并生成 JAR。
- 当前 `pom.xml` 的坐标和 Dockerfile 对应产物 `target/aurora-springboot-0.0.1.jar`，不要随意改名。

确认产物存在：

```bash
ls -lh target/aurora-springboot-0.0.1.jar
test -s target/aurora-springboot-0.0.1.jar
jar tf target/aurora-springboot-0.0.1.jar | head -n 30
```

命令说明：

- `ls -lh`：`-l` 显示文件详情，`-h` 用易读单位显示大小；阶段 1 产物约 106 MiB，可用于发现明显异常，但不是固定验收值。
- `test -s`：确认文件存在且大小大于 0；成功时没有输出，失败时退出码非 0。
- `jar tf`：`t` 表示列出归档内容，`f` 表示后面跟 JAR 文件；用于排除空包或明显损坏。
- `head -n 30`：只展示前 30 项，避免输出过多。

### 5.3 Aurora 管理端

在 `aurora-vue/aurora-admin` 目录执行：

```bash
npm ci
npm run build
```

命令说明：

- `npm ci`：按 `aurora-admin/package-lock.json` 做干净、可复现的依赖安装；必须在 `aurora-vue/aurora-admin` 目录执行。
- `npm run build`：执行当前 `package.json` 中的 `vue-cli-service build`，进行生产优化并生成 `dist/`。

检查产物：

```bash
test -f dist/index.html
du -sh dist
find dist -maxdepth 2 -type f | sort | head -n 30
```

命令说明：

- `test -f dist/index.html`：确认生产入口文件存在且是普通文件。
- `du -sh dist`：`-s` 汇总目录总大小，`-h` 用易读单位显示。
- `find ... -maxdepth 2 -type f`：列出 `dist` 中最多两层的普通文件。
- `sort`：稳定排序，方便不同构建之间对比。
- 包体积警告不会阻止阶段 1 发布，但应记录；真正的编译错误或非 0 退出码才表示不能继续。

## 6. 开发机：组装阶段 1 发布包

以下命令表达的是打包结构。路径应按开发机上的实际项目位置调整。

```bash
stage1_release_dir=/path/to/releases/luoyun-stage1
mkdir -p "$stage1_release_dir"

cp /path/to/aurora-springboot/target/aurora-springboot-0.0.1.jar \
  "$stage1_release_dir/"

tar -czf "$stage1_release_dir/aurora-admin-dist.tgz" \
  -C /path/to/aurora-admin/dist .

tar -czf "$stage1_release_dir/luoyun-provider-src.tgz" \
  -C /path/to/prepared-luoyun-provider-package .

cp /path/to/aurora-springboot/sql/music-netease-provider-v1-resource-forward.sql \
  "$stage1_release_dir/"
cp /path/to/aurora-springboot/sql/music-netease-provider-v1-resource-rollback.sql \
  "$stage1_release_dir/"
```

命令说明：

- `stage1_release_dir=...`：设置当前 Shell 变量；等号两侧不能有空格。示例路径必须替换为开发机真实路径。
- `mkdir -p`：递归创建发布目录；目录已存在时不报错。
- 双引号包裹 `"$stage1_release_dir"`：防止路径中有空格时被拆成多个参数。
- `cp <源 JAR> <目标目录>`：复制后端 JAR，不修改 `target/` 中的原产物。
- `tar -czf`：`-c` 创建归档，`-z` 使用 gzip，`-f` 指定输出文件。
- `-C /path/to/aurora-admin/dist .`：先进入 `dist` 再打包其中内容，避免解压后多出一层 `dist/`。
- Provider 的 `-C` 必须指向已经筛选和验证的最小运行目录，不能直接指向包含凭证或 `node_modules` 的项目根目录。
- 两条 SQL `cp` 分别复制前向权限脚本和对应回滚脚本。

这里的 `prepared-luoyun-provider-package` 是阶段 1 已经完成独立构建验证的最小运行目录，不是未经筛选的 Luoyun 项目根目录。Provider 压缩包解开后至少应有：

```text
Dockerfile
.dockerignore
package.json
package-lock.json
server/provider/server.ts
server/provider/security.ts
server/core/
server/http.ts
```

如果阶段 1 使用的是单独准备的 Provider Dockerfile，应以已经完成构建测试的文件为准，不要临时换基础镜像或 Node 主版本。

### 6.1 生成 SHA-256

macOS：

```bash
cd "$stage1_release_dir"
shasum -a 256 \
  aurora-admin-dist.tgz \
  aurora-springboot-0.0.1.jar \
  luoyun-provider-src.tgz \
  music-netease-provider-v1-resource-forward.sql \
  music-netease-provider-v1-resource-rollback.sql \
  > SHA256SUMS
```

命令说明：

- `cd "$stage1_release_dir"`：让摘要清单记录相对文件名，便于上传后在服务器原地校验。
- `shasum -a 256`：macOS 使用 `shasum`，`-a 256` 选择 SHA-256 算法。
- 行尾反斜杠 `\`：表示同一命令在下一行继续；反斜杠后不能再放空格或注释。
- `> SHA256SUMS`：创建或覆盖摘要清单。

Linux：

```bash
cd "$stage1_release_dir"
sha256sum \
  aurora-admin-dist.tgz \
  aurora-springboot-0.0.1.jar \
  luoyun-provider-src.tgz \
  music-netease-provider-v1-resource-forward.sql \
  music-netease-provider-v1-resource-rollback.sql \
  > SHA256SUMS
```

- `sha256sum`：Linux 常用 SHA-256 工具，输出格式可被服务器上的 `sha256sum -c` 直接读取。

检查目录：

```bash
ls -lh "$stage1_release_dir"
du -sh "$stage1_release_dir"
```

- `ls -lh`：核对发布物名称、数量与单文件大小。
- `du -sh`：核对整个发布目录总大小，判断上传和服务器磁盘空间是否足够。

## 7. 上传发布包

服务器已经配置 SSH 公钥登录，本地可直接使用：

```bash
ssh blog
```

- `ssh`：建立加密的远程 Shell 连接。
- `blog`：本机 SSH 配置中的服务器别名，应映射到正确主机、用户和公钥。登录后要核对主机，不要混淆测试与生产环境。

先创建服务器发布目录：

```bash
ssh blog 'mkdir -p /home/blog/aurora/releases/luoyun-stage1'
```

- `ssh blog '<远端命令>'`：无需进入交互 Shell，直接在服务器执行单引号内命令。
- `mkdir -p`：递归创建服务器发布目录，目录已存在时保持不变。
- 单引号保证这段命令由远端 Shell 解释，而不是被本地提前展开。

上传文件：

```bash
scp -r /path/to/releases/luoyun-stage1/* \
  blog:/home/blog/aurora/releases/luoyun-stage1/
```

命令说明：

- `scp`：通过 SSH 加密传输文件。
- `-r`：递归复制；现有发布物都是普通文件，保留该参数是为了沿用原命令并兼容以后出现子目录。
- `*`：由本地 Shell 展开，只匹配非隐藏项；发布包本来就不应包含隐藏的 `.env`。
- `blog:`：冒号前是远端主机别名，冒号后是远端绝对路径。
- 目标路径末尾 `/`：明确目标是目录。
- `scp` 成功只说明传输完成，不代表文件一定正确；服务器端仍必须执行 SHA-256 校验。

不要通过聊天记录、命令参数或发布包传输服务令牌和 `MUSIC_U`。

- 没有 Swap，且可用内存已经很低；

- MySQL、Redis、RabbitMQ、MinIO 或 Nginx 本来就不健康；
- 后端正在持续重启；
- 存在尚未定位的数据异常。

### 8.3 当前后端和前端

```bash

du -sh frontend/admin

docker compose exec backend sh -c \
```

- `du -sh frontend/admin`：汇总当前线上管理端目录大小，供替换后对比。
- `docker compose exec backend sh -c '...'`：进入 backend 容器执行 Shell 片段。
- `tr "\0" " " < /proc/1/cmdline`：把 Linux 进程参数中的 NUL 分隔符转换为空格，以可读方式查看 PID 1 的 Java 启动参数。

## 9. 一次性前置处理：Swap 与 Certbot

### 9.1 Swap

阶段 1 实际部署前已经创建 1 GiB Swap，并确认写入 `/etc/fstab`：

```text
/swapfile none swap sw 0 0
```

以后重跑阶段 1 不需要重复创建，只需检查：

```bash
free -m
sudo swapon --show
grep '^/swapfile ' /etc/fstab
```

### 9.2 Certbot 重启循环

阶段 1 前曾出现 Certbot 把整段 Shell 命令当成配置文件名的错误，并累计大量重启次数。Compose 中正确的核心写法是：

```yaml
certbot:
  image: certbot/certbot
  restart: unless-stopped
  command: /bin/sh -c "trap exit TERM; while :; do certbot renew --webroot -w /var/www/certbot --quiet; sleep 12h & wait $${!}; done"
```

修改后重建并验证：

```bash
docker compose up -d --force-recreate certbot
docker compose ps certbot
docker compose logs --tail=30 --no-log-prefix certbot
docker inspect aurora-certbot-1 \
  --format 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} RestartCount={{.RestartCount}}'
```

阶段 1 实际验收值为：

```text
Status=running ExitCode=0 RestartCount=0
```

## 10. 服务器：创建完整部署前备份

### 10.1 创建受限备份目录

```bash

stage1_backup=/home/blog/aurora/backups/luoyun-stage1-$stage1_stamp
install -d -m 700 "$stage1_backup"

```

命令说明：

- `$(date +%Y%m%d-%H%M%S)`：执行 `date` 并用年月日、时分秒生成本次发布标记。
- `stage1_backup=...`：用同一时间戳生成唯一备份目录；等号两侧不能有空格。
- `install -d -m 700`：创建目录并设为仅所有者可读、写、进入。


- `tar -czf`：创建 gzip 压缩包。
- `-C ... .`：进入当前管理端目录后打包其内部内容，便于原样恢复。

### 10.4 备份数据库

```bash
docker compose exec -T mysql sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --quick --routines --triggers --events \
  --set-gtid-purged=OFF --databases aurora' \
  > "$stage1_backup/aurora-before-luoyun-stage1.sql"
```

命令说明：

- `docker compose exec -T mysql`：在 MySQL 服务容器中执行命令，`-T` 禁用伪终端，避免重定向文件混入控制字符。
- `sh -c '...'`：由容器内 Shell 读取容器中的 `MYSQL_ROOT_PASSWORD`，不在宿主机展开密码。
- `exec mysqldump`：让 `mysqldump` 替换 Shell 进程并正确传递退出状态。
- `-uroot`：使用 root 用户；`-p"$MYSQL_ROOT_PASSWORD"` 从容器环境变量读取密码。
- `--single-transaction`：对支持事务的表创建一致性快照，减少锁表影响。
- `--quick`：逐行读取，降低大表导出时的内存占用。
- `--routines --triggers --events`：同时备份存储过程、触发器和事件。
- `--set-gtid-purged=OFF`：不写入 GTID 清理语句，降低跨实例恢复冲突。
- `--databases aurora`：包含数据库级语句并只备份 `aurora`。
- `>`：把标准输出写入指定 SQL 文件。

校验数据库备份：

```bash

ls -lh "$stage1_backup/aurora-before-luoyun-stage1.sql"
```

### 10.5 记录当前镜像和容器配置

在构建新镜像前，先给当前正在运行的镜像增加带时间戳的回滚标签：

- `docker inspect <容器> --format '{{.Image}}'`：从现有容器精确获取它正在使用的镜像内容 ID，而不是猜测标签。

## 12. Compose 接入方式

阶段 1 的关键设计是让 Provider 与 backend 共用网络命名空间：

```yaml
services:
  backend:
    image: aurora-backend:luoyun-stage1
    build: ./backend
    environment:
      LUOYUN_PROVIDER_ENABLED: "true"
      LUOYUN_PROVIDER_BASE_URL: http://127.0.0.1:5680
      LUOYUN_SERVICE_TOKEN: ${LUOYUN_SERVICE_TOKEN}

  luoyun-provider:
    image: aurora-luoyun-provider:stage1
    build: ./luoyun-provider
    restart: always
    network_mode: service:backend
    mem_limit: 160m
    pids_limit: 64
    environment:
      LUOYUN_SERVICE_PORT: "5680"
      LUOYUN_SERVICE_TOKEN: ${LUOYUN_SERVICE_TOKEN}
    volumes:
      - ./luoyun-data:/root/.config/luoyun
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://127.0.0.1:5680/v1/health >/dev/null || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
```

可以把以上内容放入 Compose 自动加载的 `docker-compose.override.yml`，但必须备份原文件。

关键点：

1. Provider 不配置 `ports`，外网和宿主机均不直接暴露 5680；
2. Provider 仍只监听 `127.0.0.1`；
3. backend 通过相同网络命名空间访问 `127.0.0.1:5680`；
4. backend 不应反向 `depends_on` Provider，否则与 `network_mode: service:backend` 形成循环依赖；
5. Provider 会话目录持久化到 `./luoyun-data`；
6. 宿主机上的 `luoyun-data` 和 `.env` 都不能提交 Git。

验证 Compose 能识别新服务：

```bash
cd /home/blog/aurora
docker compose config --services
```

- `docker compose config --services`：解析 Compose 文件和自动加载的 override 后只输出服务名。输出必须包含 `backend` 与 `luoyun-provider`；YAML 解析失败时不要继续。

期望新增：

```text
luoyun-provider
```

```bash
docker compose logs --tail=50 nginx
```

- `curl -I`：只请求响应头，用于快速检查状态码和 Nginx 可达性。
- `logs --tail=50 nginx`：读取 Nginx 最近 50 行日志。

本阶段管理端通常通过宿主机目录挂载给 Nginx，替换 `frontend/admin` 后一般不需要重新构建 Nginx 镜像。页面正常时不要为了“保险”重启整个 Compose 项目。

如果本次同时修改了 Nginx 配置，必须先做语法检查：

```bash
docker compose exec nginx nginx -t
```

- 第一个 `nginx` 是 Compose 服务名，第二个 `nginx` 是容器内可执行文件。
- `-t`：只检查配置语法和引用文件，不重载服务。

只有 `nginx -t` 成功后才平滑重载：

```bash
docker compose exec nginx nginx -s reload
```

- `-s reload`：向 Nginx 主进程发送重载信号，尽量不中断现有连接。

若静态目录交换后容器仍引用旧目录 inode，可只重建 Nginx：

```bash
docker compose up -d --force-recreate nginx
```

- `--force-recreate`：即使 Compose 配置未变也重新创建指定容器。
- 只指定 `nginx`，不要无条件重建所有服务。

浏览器使用生产域名访问管理后台，并进行强制刷新，避免旧 JS 缓存造成“后端已经更新、页面仍是阶段 0”的假象。

## 18. 常见报错、停止条件与故障定位

遇到以下任一情况应停止继续替换：

| 现象 | 处理 |
|---|---|
| `npm ci` 报锁文件不一致 | 回到开发分支修正 `package.json` 与锁文件，不在生产服务器临时改依赖 |
| `npm run build` 找不到模块 | 核对 Node 版本，在正确的 `aurora-admin` 目录重新执行 `npm ci` |
| Maven 报 `invalid target release` | 构建 JDK 与项目目标版本不兼容；切回项目已验证 JDK，不临时提升生产 Java |
| JAR 已生成但 Docker `COPY` 失败 | 核对固定文件名 `aurora-springboot-0.0.1.jar` 和 `backend` 构建上下文 |
| `scp: No such file or directory` | 用 `ls` 核对本地发布目录，并先用远端 `mkdir -p` 创建目标目录 |
| 发布包校验失败 | 重新上传并完整复验 |
| 数据库备份为空或不完整 | 不执行 SQL，不替换容器 |
| `docker build` 找不到文件 | 当前构建上下文错误或 `.dockerignore` 排除了必要文件；回到 Dockerfile 所在的已验证目录构建 |
| `docker image ls` 报参数过多 | 一条命令后写了两个仓库名；改为分别执行两条 `docker image ls <仓库>` |
| Provider 构建测试不健康 | 检查镜像、Node 版本、令牌和启动日志 |
| Provider 超过 160 MiB 或 OOM | 停止接入，先定位内存问题 |
| Compose 出现依赖循环 | 删除 backend 对 Provider 的反向 `depends_on` |
| backend 连接立即重置 | 先等待启动预热并检查日志 |
| 60 秒后仍连接重置 | 停止验收，检查启动失败或容器重启 |
| 页面仍是旧版本 | 检查 admin 目录、Nginx 挂载和浏览器缓存 |
| Nginx `nginx -t` 失败 | 不要重载；按报错文件和行号修复配置，再重新检查语法 |
| 接口 403 | 检查权限 SQL 和 admin 角色映射 |
| 接口 502/Provider unavailable | 检查共享网络、令牌和 Provider 健康 |
| Certbot RestartCount 增长 | 先修复 command 引号和 `$${!}` 转义 |
| 日志出现 `MUSIC_U` 明文 | 立即停止，清理日志并轮换网易云会话 |

最小日志集合：

```bash
docker compose ps
docker compose logs --tail=200 backend
docker compose logs --tail=200 luoyun-provider
docker compose logs --tail=50 nginx
docker inspect aurora-backend-1 \
  --format 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} RestartCount={{.RestartCount}} OOMKilled={{.State.OOMKilled}}'
docker inspect aurora-luoyun-provider-1 \
  --format 'Status={{.State.Status}} ExitCode={{.State.ExitCode}} RestartCount={{.RestartCount}} OOMKilled={{.State.OOMKilled}}'
```

- `docker inspect --format`：只提取状态、退出码、重启次数和 OOM 标记，避免把包含环境变量的完整配置倾倒到共享日志。
- 收集到足以区分构建、启动、网络、权限或资源问题的证据后停止，不要反复执行同一个失败操作。

## 19. 回滚方案

回滚属于生产变更，只能在明确确认回滚目标、备份目录和影响范围后执行。

### 19.1 优先回滚应用，不立即恢复整个数据库

阶段 1 对数据库只增加权限资源，因此通常按以下顺序回滚：

1. 停止新 Provider；
2. 恢复旧 backend JAR 和 Compose 配置；
3. 恢复旧管理端；
4. 重建并启动旧 backend；
5. 验证旧业务；
6. 最后执行阶段 1 权限回滚 SQL。

### 19.2 停止 Provider

```bash
cd /home/blog/aurora
docker compose stop luoyun-provider
```

不要删除 `luoyun-data`，这样可以保留会话文件供问题分析或后续恢复；该目录仍应保持受限权限。

### 19.3 恢复后端和管理端

先设置准确备份路径：

```bash
stage1_backup=/home/blog/aurora/backups/luoyun-stage1-YYYYMMDD-HHMMSS
test -d "$stage1_backup"
```

恢复 JAR：

```bash
install -m 644 \
  "$stage1_backup/aurora-springboot-0.0.1.jar" \
  /home/blog/aurora/backend/aurora-springboot-0.0.1.jar
```

恢复管理端前，先保留失败版本：

```bash
cd /home/blog/aurora
mv frontend/admin frontend/admin.failed-luoyun-stage1
mkdir frontend/admin
tar -xzf "$stage1_backup/frontend-admin-before-stage1.tgz" \
  -C frontend/admin
```

恢复 Compose 和 `.env` 时必须先人工比较，避免覆盖部署后新增的无关配置：

```bash
diff -u docker-compose.yml "$stage1_backup/docker-compose.yml" || true
```

确认后再恢复对应文件。不要用递归覆盖整个 `/home/blog/aurora`。

### 19.4 重建旧后端

优先确认前面保留的回滚镜像仍存在：

```bash
docker image ls aurora-backend
docker image ls aurora-luoyun-provider
```

如果 Compose 的 backend 明确配置了 `image:`，可将其临时指向准确标签：

```text
aurora-backend:rollback-YYYYMMDD-HHMMSS
```

Provider 如需恢复，则使用同一次部署对应的：

```text
aurora-luoyun-provider:rollback-YYYYMMDD-HHMMSS
```

修改前先确认时间戳与备份目录完全一致。然后禁止重新构建，直接用旧镜像启动：

```bash
cd /home/blog/aurora
docker compose up -d --no-build backend
docker compose ps
docker compose logs --tail=100 backend
```

- `--no-build`：禁止 Compose 在启动时触发构建，确保使用已保留的回滚镜像。
- 如果 Compose 只有 `build:`、没有可切换的 `image:`，则按原流程恢复旧 JAR、Dockerfile 和 Compose，再执行下面的重新构建。

需要从旧构建输入重建时：

```bash
cd /home/blog/aurora
docker compose build backend
docker compose up -d backend
docker compose ps
docker compose logs --tail=100 backend
```

- `docker compose build backend`：只按已恢复的旧 JAR 与 Dockerfile 重建 backend，不重建其他服务。
- 回滚验收完成前继续保留失败版本目录、新旧镜像和数据库备份。

### 19.5 回滚权限 SQL

仅在旧后端已经恢复、确认不再需要阶段 1 接口后执行：

```bash
docker compose exec -T mysql sh -c \
  'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" aurora' \
  < releases/luoyun-stage1/music-netease-provider-v1-resource-rollback.sql
```

执行后重新查询 `t_resource` 和 `t_role_resource`，确认只移除了阶段 1 新增的网易云管理权限。

### 19.6 完整数据库恢复是最后手段

只有在确认数据库出现无法通过前向修复或权限回滚解决的破坏时，才考虑使用完整 SQL 备份恢复。完整恢复会覆盖阶段 1 部署后产生的其他业务数据，必须先停止写入、确认恢复时间点并再次备份当前数据库。

## 20. 阶段 1 的关键工程结论

1. **低内存服务器仍可采用独立 Provider。** 实际常驻约 44 MiB，160 MiB 限制有足够余量。
2. **Provider 必须模块化。** Spring Boot 只依赖稳定的 `/v1/*` 契约，不直接搬入 Luoyun 的网易云实现。
3. **5680 不应公开。** 共享 backend 网络命名空间后，两者可通过 loopback 通信。
4. **权限 SQL 必须先于新后端对外。** 管理接口不能依赖未知路径的默认行为。
5. **MUSIC_U 与服务令牌是两类凭证。** 前者代表网易云账号，后者只保护内部 Provider API，不能混用。
6. **替换必须使用临时路径和可恢复移动。** 不直接覆盖旧 JAR 和管理端目录。
7. **验证必须分层。** Provider 健康、Spring Boot 代理、Nginx、浏览器和资源占用要分别验证。
8. **启动预热与持续故障要区分。** 约 10 秒的短暂连接重置可观察，超过停止条件则必须调查。
9. **构建测试容器必须删除，镜像可以保留。** 临时容器不承载数据，生产会话目录则必须持久化。
10. **阶段 1 只读边界是后续阶段的安全基线。** 阶段 2 的数据库写入、队列和媒体存储应建立在这条链路稳定之后。

## 21. 最短执行顺序

需要快速复盘时，只看以下顺序：

```text
Vue：npm ci → npm run build → 检查 dist → 压缩

  → 临时容器健康与内存验证
  → 配置共享 backend 网络命名空间
```
